网络安全：如何扛住有组织的攻击

攻击者不会按你的架构图出牌。他们会找最薄的那一环，反复试， 直到找到能撬开的缝。这一章讲的是如何把系统做成「没有最薄的那一环」—— 威胁建模、纵深防御、密钥管理、内控，以及当防线真的被突破时该怎么办。

本章回答
面对有组织的持续攻击，系统靠什么活下来
关键产出
威胁模型 · 纵深防御体系 · 密钥管理方案 · 应急响应预案

06.1威胁建模：先搞清楚敌人在哪

安全建设最常见的失败不是「防护不够强」，而是防错了方向。 花大力气加固了 A 面墙，攻击者从没人看的 B 面进来。 威胁建模就是为了避免这种浪费。

一个实用的建模方法是按攻击者画像分类，因为不同画像的 能力、动机、持久度完全不同，对应的防护重点也不同。

攻击者能力动机主要手段防护重点
脚本小子低，用现成工具炫耀 / 小额获利扫描器、已知漏洞利用、撞库基础加固、WAF、限流
自动化黑产中，有工具链规模化获利批量注册、薅羊毛、爬虫、撞库设备指纹、行为风控、验证码
专业犯罪组织高，有资金与耐心直接盗取资产钓鱼、供应链投毒、定向渗透、买通内部人员密钥隔离、内控、审计、最小权限
内部人员高，有合法权限获利 / 报复越权操作、数据导出、植入后门四眼原则、权限分离、操作留痕
国家级行为体极高，有 0day情报 / 破坏0day 利用、供应链攻击、长期潜伏假设已失陷、零信任、快速检测与响应
建模的核心产出

威胁建模的产出不是一份报告，而是一组「假设已被攻破」的应对方案。 对每个关键资产，问三个问题：攻击者要拿到它必须突破哪些环节？ 突破后能造成多大损失？如何尽早发现？ 第三个问题最重要 —— 假设失陷不可避免，检测与响应能力才是最终防线。

攻击面梳理

把系统所有「能被外部触达」的入口列全，是建模的第一步。常见的遗漏点：

  • 内部管理后台 —— 往往比面向用户的系统更弱，却拥有更高权限。
  • 运维通道 —— SSH、跳板机、CI/CD 系统。攻破 CI 等于可以往生产环境部署任意代码。
  • 第三方回调接口 —— 支付回调、短信回调、链上 webhook。如果不验签，可以被伪造。
  • 移动端 App —— 可以被反编译，硬编码的密钥会直接暴露。
  • 依赖库 —— 一个被投毒的 npm 包可以拿到构建环境的全部权限。
  • 员工个人设备 —— 钓鱼邮件是最有效的入侵方式，没有之一。

06.2纵深防御：让攻击者必须连续成功

纵深防御（Defense in Depth）的核心思想是： 不假设任何单一防线不会被突破。 每一层都可能失效，但攻击者必须连续突破所有层才能拿到资产。 假设每层被突破的概率是 10%，五层叠起来就是 0.001%。

图 06-A 七层纵深防御。前四层阻止攻击，后三层限制损失并发现异常。注意第 7 层的存在意味着整个体系承认「前面的防线可能全部失效」—— 这不是悲观，而是工程上唯一诚实的假设。

06.3接入层：处理掉 90% 的噪音

DDoS：两种完全不同的攻击

「抗 DDoS」这个词把两类差异极大的攻击混在了一起。 分开看才知道该用什么手段。

四层攻击 · 流量型
  • SYN Flood、UDP 反射、DNS 放大
  • 特征是流量巨大，可达数百 Gbps
  • 目的是耗尽带宽与连接表
  • 应对：流量清洗中心、Anycast 分散、运营商联动
  • 单靠自身机房无法抵御，必须依赖上游
七层攻击 · 应用型
  • CC 攻击、慢速连接、API 高频调用
  • 特征是流量不大但请求复杂，每个请求看起来都合法
  • 目的是耗尽应用的计算与数据库资源
  • 应对：行为分析、人机验证、动态限流、缓存
  • 无法靠「加大带宽」解决，必须靠识别
最容易被打穿的地方

七层攻击中最难防的是「慢速攻击」： 攻击者建立大量连接，每个连接以极慢的速度发送数据， 让服务器长时间保持连接等待。每个连接消耗极少资源， 但成千上万个连接会耗尽服务器的连接池。

防御手段是设置全生命周期的超时 —— 不仅要有读超时，还要有「请求头读取超时」「请求体接收超时」 「整体处理超时」。很多框架默认只设了读超时，于是慢速攻击长驱直入。

限流：保护自己，而不是惩罚用户

限流的目的不是「限制用户」，而是在过载时保住核心功能。 一个没有限流的系统在流量洪峰下会整体崩溃， 而有限流的系统会优雅地拒绝一部分请求，保住其余部分。

限流策略 · 分层设计
# 分层限流：粒度从粗到细，越细的限流越贵

# 1. IP 级 —— 最粗，成本最低，防单点刷接口
limit_req_zone $binary_remote_addr zone=perip:10m rate=50r/s;

# 2. 用户级 —— 按 API Key 限流，区分普通用户与做市商
#    做市商需要更高的配额，且不应与普通用户共享限额池
limit_req_zone $http_x_api_key zone=perkey:20m rate=100r/s;

# 3. 接口级 —— 不同接口的价值不同，限额也应不同
#    下单接口：10 r/s（有实际成本，需要冻结资金）
#    查询接口：200 r/s（纯读，成本低）
#    提现接口：1 r/10s（极高风险）

# 4. 全局级 —— 最后一道保护，防止整体过载
#    当系统负载超过阈值时，主动拒绝非核心请求，保住撮合与结算

# 关键原则：限流必须是「快速失败」，不能排队等待
# 排队会让延迟飙升，最终演变成雪崩 —— 立即返回 429 反而更友好

06.4应用层：那些年复一年被利用的漏洞

OWASP Top 10 已经发布了很多年，但每年被利用的漏洞类型几乎没变。 原因是这些漏洞的根源在于「开发者图省事」，而不是技术难度高。

漏洞根源正确做法
SQL 注入 字符串拼接 SQL 参数化查询（预编译）。ORM 也要注意 Raw() 之类的逃逸口
XSS 把用户输入直接当 HTML 渲染 输出编码 + CSP 头。富文本必须用白名单过滤，不能用黑名单
SSRF 服务端按用户提供的 URL 发起请求 白名单域名 + 禁止访问内网地址段 + 禁止跟随重定向到内网
越权访问 只校验「已登录」，不校验「是不是你的」 每个资源访问都校验归属关系。用不可枚举的 ID，但不能只靠 ID 不可猜
CSRF 浏览器自动携带 Cookie SameSite Cookie + CSRF Token。敏感操作额外要求二次验证
反序列化 反序列化不可信数据 不使用原生反序列化，改用 JSON 等纯数据结构格式
交易系统特别要注意的两条

① 金额字段绝不接受客户端传入的「最终值」。 比如手续费，应该由服务端按规则计算，而不是接受客户端传来的手续费数字。 任何「客户端说多少就是多少」的字段，都是潜在的资金漏洞。

② 状态字段同样不可信。 订单状态、用户等级、风控标记，这些必须服务端决定。 客户端传来的状态只能作为「请求意图」，不能作为事实。

认证：从密码到 Passkey

交易系统的认证要求高于普通应用，因为账号被盗直接等于资产损失。

  1. 密码用 Argon2id 或 bcrypt 加盐哈希，绝不用 MD5/SHA1。密码强度用「长度」而非「复杂度」要求 —— 长度对抗暴力破解更有效。
  2. 多因素认证TOTP 优于短信（SIM 卡可被克隆）。恢复码必须离线保存且一次性使用。绑定 MFA 后的首次提现应额外延迟。
  3. Passkey / WebAuthn用设备生物识别代替密码，私钥存在设备安全芯片中，无法被钓鱼。这是目前抗钓鱼能力最强的方案，应当作为首选推荐。
  4. 会话管理会话 ID 足够随机（≥128 位）、绑定设备指纹、敏感操作要求重新验证、异地登录立即告警、提供「登出所有设备」。

06.5业务风控：识别「像人的机器」

应用层防护能拦住技术漏洞，但拦不住「用合法接口做非法的事」。 批量注册、薅羊毛、对敲刷量、盗号提现 —— 这些请求在技术上完全合法， 只能靠业务风控识别。

设备指纹：认出「同一个来源」

攻击者可以轻易换 IP，但很难完全改变设备特征。设备指纹通过 收集浏览器/设备的软硬件特征组合，生成一个稳定的标识：

  • 被动浏览器与硬件特征。Canvas 渲染差异、WebGL 参数、字体列表、时区、屏幕参数、CPU 核心数。组合起来有极高的唯一性。
  • 主动轻量探测脚本。在用户无感知的情况下采集少量额外特征。注意隐私合规，且必须可被用户拒绝。
  • 行为交互模式。鼠标轨迹、点击精度、输入节奏、页面停留时间。机器人的行为模式与真人差异明显。
组合信号才有意义

单一信号几乎都可以被绕过，但组合起来就非常有效： 「同一设备指纹 + 十个不同账号 + 五分钟内」 这个组合几乎可以确定是自动化攻击。 风控系统的核心能力不是采集多少信号， 而是把信号组合成有判别力的规则与模型。

风控的三档处置

ALLOW

放行

评分低，正常执行。绝大多数请求走这条路，风控不能成为性能瓶颈。

CHALLENGE

挑战

评分中等，要求额外验证：人机验证、短信验证、二次确认。让真人顺利通过，让机器成本升高。

BLOCK

拦截

评分高，直接拒绝并记录。同时触发告警，供安全团队分析是否为新型攻击。

风控最重要的指标

不是「拦截了多少攻击」，而是误杀率。 一个把 5% 正常用户挡在门外的风控系统，即使拦住了所有攻击， 也是在摧毁业务。因此风控必须： ① 有快速申诉通道； ② 对「挑战」优先于「拦截」； ③ 每次规则变更都评估误杀率； ④ 记录被拦截样本供持续优化。

06.6密钥与机密：最不该泄露的东西

系统里有很多「机密」：数据库密码、API 密钥、签名私钥、加密密钥。 它们一旦泄露，前面所有的防护都可能被绕过。

三个绝对不能犯的错误

禁止
  • 把密钥硬编码在源码里（尤其前端与移动端）
  • 把密钥提交到 Git 仓库（历史记录同样危险）
  • 把密钥打进日志或错误堆栈
  • 用同一把密钥加密所有数据
  • 密钥长期不轮换
  • 把生产密钥给开发环境用
正确做法
  • 用密钥管理服务（KMS / Vault）集中管理，按需下发、短期有效
  • 提交前用扫描工具拦截（gitleaks / trufflehog）
  • 日志系统配置敏感字段自动脱敏
  • 按用途与数据域分离密钥，一个泄露不影响其他
  • 定期轮换，且有自动化流程保证轮换不出故障
  • 环境之间完全隔离，密钥不互通

加密的分层

「加密存储」不是一个动作，而是一套分层策略。 关键是搞清楚加密密钥本身存在哪里 —— 如果加密密钥和数据放在同一个地方，加密就只是心理安慰。

图 06-B 分层加密。安全性来自「解密所需的东西不在被拖走的数据库里」。这是加密是否有意义的唯一判据。

06.7内控：防住「有权限的自己人」

外部攻击者要突破很多层，而内部人员已经站在里面了。 所有资金事故里，内部人参与的比例远高于公众想象。 内控的目标不是「不信任员工」，而是让任何人单独行动都无法造成不可挽回的损失。

最小权限

权限应当按「完成工作所必需」来授予，而不是「方便」。 具体做法：

  • 默认拒绝 —— 权限需要显式申请与审批，而不是默认拥有。
  • 按角色而非按人 —— 角色定义清晰的职责边界，人员变动时只改角色归属。
  • 时限授权 —— 生产环境的高危权限应「临时申请、用完即撤」，而不是永久持有。
  • 定期复查 —— 每季度审查一次权限，撤销不再需要的。人升职、转岗后往往留着旧权限。
  • 生产数据脱敏 —— 开发和测试环境不应有真实用户数据。

四眼原则

任何高危操作都必须至少两个人独立确认，且两人不能是同一人、 不能共用账号、最好不在同一团队。适用于：

操作为什么需要双人
大额提现审批单人可批 = 单人可偷。双人审批让内部作案需要串通
冷钱包转账动用的是绝大多数资产，必须多人多地把分片凑齐
生产数据库直连直连意味着可以绕过所有应用层控制
修改用户余额人工调账是最容易被滥用的权限
发布生产版本可以借发布植入后门
修改风控规则放宽规则可以为后续攻击铺路
审计日志必须防「审计者」

如果写审计日志的人可以删审计日志，那审计就形同虚设。 因此审计日志必须： ① 写入独立系统，应用账号只有写权限； ② 采用哈希链，删除或修改会被发现； ③ 定期导出到外部存储，平台自己也无法回改； ④ 有独立的访问控制，看审计日志本身也是一项需要授权的操作。

06.8供应链与数据安全：被忽视的两个战场

供应链：你信任的依赖可能在害你

现代软件大量依赖第三方库。一个被投毒的依赖包， 可以在构建时就拿到你的全部机密，或者在运行时植入后门。

  • 锁定锁定依赖版本。使用 lockfile，且锁定文件必须提交到仓库。避免「自动升级到最新版」带来的意外。
  • 审计依赖漏洞扫描。接入 CI，发现高危漏洞即阻断构建。同时维护 SBOM（软件物料清单），知道自己在用什么。
  • 验证校验完整性。启用包管理器的签名与哈希校验。私有依赖要确认来源可信。
  • 隔离构建环境隔离。构建过程不应能访问生产机密。构建产物签名后再部署，部署端校验签名。

数据安全：分类、脱敏、留存

不是所有数据都同等重要，但很多系统对所有数据一视同仁， 结果是既浪费了加密成本，又没保护好真正敏感的部分。

级别示例保护要求
极高私钥、种子、助记词离线保管 / HSM，绝不出现在任何联网系统
高身份证号、银行卡、密码哈希加密存储，密钥与数据分离，访问需授权并留痕
中手机号、邮箱、交易记录加密或脱敏存储，日志中必须脱敏
低公开行情、K 线数据无特殊要求，可缓存与分发

06.9检测、响应与演练：假设防线会被突破

前面八节都在讲「怎么防住」。但真实世界里， 再强的防御也可能被突破。所以最后一个问题至关重要： 当防线真的被突破时，系统能在多久内发现、多久内止损？

图 06-C 应急响应五步。第 ③ 步「止损」必须排在第 ④ 步「查原因」之前。这是最反直觉、也最容易被搞错的一点 —— 现场人员往往急于搞清楚发生了什么，但每多等一分钟，损失就多一分。先关门，再查案。

关键指标

MTTD（平均检测时间）和 MTTR（平均响应时间）是衡量安全能力最实在的两个数字。 很多团队把预算全花在「防」（买设备、上产品）， 却在「检测」上投入不足 —— 结果是攻击者已经在系统里潜伏了几个月， 而团队毫无察觉。

一个健康的比例是：防御、检测、响应三者的投入大致相当。 只投防御的系统，等于买了一扇很厚的门，却装了透明的玻璃墙。

演练：把预案变成肌肉记忆

没有演练过的预案，在真实事件发生时几乎一定失效 —— 因为没人记得步骤、找不到联系方式、不知道谁有权拍板。

  1. 桌面推演定期组织，给定一个虚构场景（例如「发现热钱包私钥可能泄露」），让各角色口头走一遍流程。成本低，能快速暴露流程缺陷。
  2. 红蓝对抗红队模拟真实攻击者（含社会工程、内部渗透），蓝队负责检测与响应。重点不是「谁赢」，而是红队用的哪条路径是蓝队没监控到的。
  3. 混沌工程在生产环境受控地注入故障（杀进程、加延迟、断网络），验证系统的容错与告警是否按预期工作。这是检验「假设失陷」能力的最直接方式。
  4. 漏洞赏金向外部安全研究者开放漏洞提交通道并给予奖励。全球有大量高水平研究者，他们的视角往往比内部团队更刁钻。关键是响应要快、沟通要专业、奖金要有诚意。
