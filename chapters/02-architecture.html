系统架构：一笔订单走过的完整旅程

架构图谁都会画，难的是说清楚「为什么这条线必须连到那里」。 本章沿着一次真实的下单请求，从用户点击按钮开始，一直走到成交回报回到屏幕上， 在每一个环节停下来问：这一步能不能省？为什么不能？

02.1全局视图：七层与三条数据流

先给全貌。一个交易系统可以拆成七个功能域， 它们之间流动着三类截然不同的数据：命令流（用户的意图）、 事件流（系统产生的事实）、查询流（读请求）。 把这三条流分开，是架构清晰的第一步。

图 02-A 全局架构。注意两点：其一，业务服务不直接写撮合内核，而是通过事件总线把命令变成有序事件；其二，行情是独立的一条旁路，它从撮合结果派生，但绝不反向影响撮合。

02.2边缘层：把 90% 的恶意流量挡在门外

边缘层的价值可以用一句话概括：在离用户最近、离核心最远的地方处理掉大部分请求。 一次 DDoS 攻击如果有 90% 的流量在边缘就被丢弃， 核心系统甚至不会感知到攻击发生过。

  • CDN静态资源与行情快照。K 线历史、交易对列表这类读多写少的数据可以缓存在边缘，减少回源压力。
  • DDoS流量清洗。区分四层攻击（SYN Flood、UDP 反射）与七层攻击（CC 攻击）。前者靠流量特征与速率限制，后者需要行为分析 —— 因为它的每个请求看起来都是合法的。
  • WAF应用层攻击拦截。SQL 注入、XSS、路径穿越、恶意爬虫。规则库要持续更新，且必须能识别针对 API 的自动化攻击。
  • LB负载均衡。交易系统的负载均衡有个特殊要求：长连接不能随意漂移。WebSocket 行情连接一旦建立，应尽量保持在同一台后端，否则每次重连都要重新同步快照。
设计原则

边缘层做的每一个决策都应该是廉价且快速的。 如果边缘层需要查数据库才能判断是否放行，那它就成了新的瓶颈， 而且攻击者只要压垮边缘层就能达到目的。正确做法是让边缘层只依赖 内存中的规则、IP 信誉库和速率计数器。

02.3API 网关：唯一允许「拒绝」的地方

网关是命令流的第一道业务关卡。它要在最短时间内回答四个问题： 你是谁、这个请求是不是重复的、你还有没有额度、 该路由到哪。四个问题全部答完才放行。

鉴权与签名：为什么不用简单的 Token

普通网站用 Session 或 JWT 就够了。但交易系统的 API 有一个额外要求： 请求不能被篡改，也不能被重放。 因为一个被重放的「提现 1 BTC」请求，等同于直接的资金损失。

签名方案 · HMAC
// 客户端构造签名：把「密钥 + 时间戳 + 随机数 + 请求体」一起哈希
timestamp = 1759999999000        // 毫秒，服务端允许 ±5 秒偏移
nonce     = "a7f3c9e1"           // 一次性随机串，服务端在时间窗内去重
body      = '{"symbol":"BTCUSDT","side":"BUY","type":"LIMIT","price":"43210.55","qty":"0.5"}'
payload   = timestamp + nonce + body
signature = HMAC_SHA256(api_secret, payload)   // 十六进制输出

// 服务端校验顺序（任何一步失败即拒绝，且记录风控日志）
// 1. 时间戳是否在 ±5s 窗口内          → 防重放（过期请求）
// 2. nonce 是否已被使用（Redis SETNX） → 防重放（窗口内重复）
// 3. 重算签名是否一致（恒定时间比较）   → 防篡改
// 4. 请求体哈希是否与签名时一致         → 防中间人改包
// 5. 权限范围是否覆盖该接口             → 防越权
细节致命

签名比较必须用恒定时间比较函数（如 hmac.Equal）， 不能用 ==。字符串比较会在第一个不同字符处提前返回， 攻击者可以通过测量响应时间逐字节猜出正确签名。 这类时序攻击在普通业务里可以忽略，在资金接口上是真实的漏洞。

02.4业务服务群：把校验做在正确的位置

一笔下单请求要经过一连串校验。问题不是「要不要校验」， 而是每一层校验什么、在哪一层校验。校验放错位置， 要么性能崩掉，要么留下漏洞。

层校验内容代价失败后果
网关身份、签名、nonce、接口级限流极低（纯内存）未授权访问
风控服务设备指纹、行为评分、频率异常、黑名单低（内存 + 缓存）被自动化攻击薅光
订单服务交易对状态、精度、最小下单量、价格笼子低脏数据进入撮合
资产服务可用余额是否充足、冻结是否成功中（需事务）透支、负余额
撮合内核仅校验最基础的结构完整性必须极低—

注意最后一行。撮合内核不做业务校验 —— 因为它是性能最敏感的地方，而且它应该只处理「已经确定合法」的输入。 让内核去查余额、查黑名单，等于把数据库访问塞进了微秒级的循环里。

「价格笼子」：一个容易被忽略的保护

价格笼子限制订单价格与市场价的偏离幅度（例如不得超过 ±10%）。 它的目的不是防止用户亏钱，而是防止因为用户输错小数点造成市场剧烈波动。 有人把 43210 打成 432100 挂出去，如果没有笼子， 做市商的自动策略会立刻吃掉这个订单，然后引发一连串连锁反应。

02.5撮合集群：一个不能水平扩展的组件

这是整个架构里最特殊的一层。绝大多数服务可以通过「加机器」来扩容， 但撮合内核不能 —— 至少不能简单地加。

原因是撮合必须满足两条硬性约束：

  1. 确定性相同的输入序列，必须产生完全相同的输出。如果两台机器并行处理同一个交易对的订单，谁先谁后是不确定的，结果就不可复现 —— 而不可复现意味着无法审计、无法重放、无法灾备。
  2. 全局有序「价格优先、时间优先」中的「时间」，指的是系统接收订单的先后顺序。这个顺序必须由一个单点统一裁定，不能由多台机器各自判断。

所以标准做法是：按交易对分片，每个分片内单线程串行。 BTC/USDT 是一个独立的分片，ETH/USDT 是另一个。它们之间互不影响， 可以分布在不同机器上，于是整体吞吐量仍然可以横向扩展 —— 只是扩展的维度是「交易对数量」，不是「单交易对的并发度」。

核心权衡

单交易对的撮合能力上限，等于单线程的处理速度。这就是为什么撮合引擎 要用 C++/Rust 写、要全内存、要避免任何系统调用 —— 它的性能天花板就是整个系统的性能天花板。 第 08 章会具体讲怎么把单线程压到极致。

02.6行情分发：把撮合结果变成你屏幕上的数字

行情是一条单向的、只读的旁路。它从撮合结果派生， 但不允许反向影响撮合。这个方向性约束非常重要 —— 它意味着即使行情系统完全崩溃，交易本身仍然可以正常进行。

为什么用「增量 + 快照」而不是全量推送

BTC/USDT 的盘口每秒可能变化上千次。如果每次都推送完整盘口（比如 50 档）， 带宽会瞬间爆炸。标准做法是：

  • 首次连接推送一份完整快照，附带一个序列号 seq=1000。
  • 之后只推送增量：seq=1001 更新第 3 档为 0.5 BTC。
  • 客户端按序列号顺序应用增量。如果发现序列号跳号（比如收到 1005 但上次是 1001），说明丢了包，客户端主动断开并重新拉取快照。
工程细节

序列号必须由撮合内核统一分配，不能由行情服务自己生成。 否则行情服务重启后序列号会重置，所有客户端都会陷入「不断重连拉快照」的死循环。 这是实践中非常常见的一个故障模式。

02.7数据层：不同数据用不同的库

交易系统的数据可以按「访问模式」分成四类， 用同一种存储去装它们，必然有一类会很难受。

STORE 01

关系库

订单、账本条目、用户、提现记录。要求强事务与唯一约束。通常按用户 ID 分库分表，账本表单独部署。

STORE 02

内存库

盘口缓存、会话、限流计数器、幂等去重表。要求亚毫秒读写，允许在故障时从持久层重建。

STORE 03

消息队列

事件流、异步任务、跨服务通知。要求分区有序与至少一次投递，消费者必须幂等。

STORE 04

列式存储

成交历史、K 线、风控日志、审计流水。要求高压缩比与聚合查询性能，写多读少、几乎不更新。

一条纪律

账本数据只追加，不修改。任何「修正」都是追加一条冲正条目， 而不是 UPDATE 原记录。这条纪律让账本天然具备可审计性 —— 你永远能看到「当时记了什么」以及「后来怎么改的」。

02.8一次下单请求的完整旅程

现在把上面所有组件串起来，跟着一笔限价买单走完全程。 注意每一步的耗时量级 —— 它们决定了系统整体延迟的构成。

图 02-B 下单时序。关键设计是第 5 步的「定序」：所有并发的请求在这里被压成一个确定性的序列，此后的一切都是串行且可复现的。第 10 步全部异步，绝不阻塞主链路 —— 这是延迟能压到 10ms 以内的原因。

为什么「先冻结再撮合」不能反

顺序不能颠倒，原因很直接：如果先撮合再冻结，可能出现「成交了但钱不够」。 用户在同一瞬间用同一笔钱下了两笔单，如果两笔都先进入撮合并成交， 结算时就会发现余额只够一笔。此时系统面临一个无法优雅解决的问题 —— 撤销哪一笔？两笔都已经成交并向市场公布，撤销任何一笔都是对市场秩序的破坏。

先冻结则把这个矛盾消灭在萌芽状态：第二笔订单在冻结阶段就会因为 「可用余额不足」而被拒绝，根本不会进入撮合。这就是 「在最早的可能点拒绝请求」这一原则的具体体现。

第 02 章 · 检查清单

① 命令流、事件流、查询流三条链路在架构上分离；
② 边缘层只依赖内存规则，不查数据库；
③ 签名校验使用恒定时间比较，nonce 有时间窗去重；
④ 业务校验分层放置，撮合内核不做业务校验；
⑤ 撮合按交易对分片，片内单线程串行；
⑥ 行情序列号由撮合内核统一分配，支持断线补齐；
⑦ 下单链路严格「先冻结、后撮合」；
⑧ 主链路只做必要动作，日志与统计全部异步。
