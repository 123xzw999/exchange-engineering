00.1需求：从一句话到可验证的问题

「做一个交易平台。」这是一句需求，但它不是一句可执行的需求。 它没有边界、没有验收标准、没有任何能判断「做完了没有」的判据。 工程上第一个真正有价值动作，是把这类句子拆成一组可被证伪的陈述。

拆分时至少要问四个问题：谁用（干系人）、在什么场景下用（用例）、 什么条件算成功（验收标准）、什么不能违反（约束）。 前三个是功能需求，最后一个往往是非功能需求 —— 而对交易系统来说， 非功能需求才是真正决定架构的东西。

维度模糊表述可验证表述
功能 用户能下单 限价单在提交后 50ms 内返回「已受理」或明确的拒绝原因码；同一订单号重复提交只成交一次
性能 系统要快 撮合内核 P99 处理延迟 < 1ms；网关端到端 P99 < 20ms；单交易对峰值 10 万笔/秒
一致性 钱不能错 任意时刻，所有账户余额之和恒等于已发行总量；日终对账差异必须为 0，否则阻断提现
可用性 不能挂 交易链路月度可用性 ≥ 99.95%；下单接口故障时必须在 200ms 内快速失败，不得挂起
安全 要安全 提现需二次验证 + 地址白名单；热钱包余额不超过总资产 5%；所有资金操作留不可篡改审计日志
经验法则

如果一条需求无法写出「什么情况下算失败」，那它就不是需求，是愿望。 「系统要安全」是愿望；「热钱包被盗后，冷钱包资产不受影响，且损失上限被保险基金覆盖」才是需求。

00.2领域建模：把现实翻译成数据结构

领域模型不是数据库表设计。它是对业务概念的抽象 —— 决定哪些名词有独立身份、哪些只是属性、哪些概念之间存在不变式。 建模错了，后面所有代码都在给这个错误打补丁。

交易系统的领域模型可以浓缩成八个核心概念。注意它们之间的关系， 尤其是 LedgerEntry 与 Balance 的关系 —— 这是第 04 章「币为什么不会消失」的根：

ENTITY 01

User

身份主体。承载 KYC 状态、风险等级、权限。一个用户可以拥有多个账户。

ENTITY 02

Account

账户容器，区分交易账户、合约账户、资金账户。账户是资金隔离的边界。

ENTITY 03

Balance

某账户下某币种的余额快照。必须拆成可用、冻结、锁定三个分量，绝不能用单一数字。

ENTITY 04

LedgerEntry

账本条目。每一次余额变动都必须由一组借贷平衡的条目解释，它是事实的唯一来源。

ENTITY 05

Instrument

可交易标的，如 BTC/USDT。定义价格精度、数量精度、最小下单量、费率档位。

ENTITY 06

Order

订单。有明确的生命周期状态机，状态迁移必须受约束，不允许任意跳转。

ENTITY 07

Trade

成交记录。一笔成交必然同时归属于两个订单（买方与卖方），这是撮合的不变式。

ENTITY 08

Position

持仓。合约场景下的风险敞口，与现货的 Balance 是两套完全不同的记账逻辑。

状态机是领域模型的核心表达

订单为什么会被写乱？因为开发者把它当成一个字符串字段，随手 UPDATE。 正确做法是把合法迁移编码进类型系统，让非法迁移在编译期或运行期直接失败。

Go
// 订单状态机：只允许列出的迁移，其余一律拒绝
type OrderState string

const (
    StateNew              OrderState = "NEW"              // 已受理，未进撮合
    StatePartiallyFilled  OrderState = "PARTIALLY_FILLED" // 部分成交
    StateFilled           OrderState = "FILLED"           // 完全成交（终态）
    StateCanceled         OrderState = "CANCELED"         // 已撤销（终态）
    StateRejected         OrderState = "REJECTED"         // 已拒绝（终态）
)

// 迁移表：显式声明「从哪儿能到哪儿」
var allowed = map[OrderState][]OrderState{
    StateNew:             {StatePartiallyFilled, StateFilled, StateCanceled, StateRejected},
    StatePartiallyFilled: {StatePartiallyFilled, StateFilled, StateCanceled},
    StateFilled:          {},  // 终态：不可再迁移
    StateCanceled:        {},
    StateRejected:        {},
}

func (o *Order) Transition(to OrderState) error {
    for _, s := range allowed[o.State] {
        if s == to {
            o.State = to
            return nil
        }
    }
    // 非法迁移：这里必须报错，而不是静默接受
    return fmt.Errorf("illegal transition %s -> %s (order %s)", o.State, to, o.ID)
}

这段代码的价值不在于「防止 bug」，而在于把业务规则从人的记忆里搬进代码。 一个新人接手时，不需要读文档就知道 FILLED 之后不能再改状态。

00.3架构：分层、边界与演进

架构的本质是划边界，而划边界只有一个目的： 让变化被限制在局部。判断一个边界划得好不好，只需问一句 —— 「这个需求变了，我要改几个服务？」

图 00-A 五层架构。关键约束是依赖只能向下：领域核心不依赖任何具体数据库，数据层可以被替换而不影响撮合逻辑。这条约束保证了「换存储引擎」不会演变成「重写系统」。

边界怎么切

三条可操作的判据，按优先级排序：

  1. 按一致性要求切需要强一致、必须在同一个事务里完成的，放一起。下单冻结资金是一个事务；发送通知不是。前者不能跨服务，后者必须跨。
  2. 按变化频率切费率规则每月改一次，撮合算法两年不动。把变化快的和变化慢的分开，避免为了改费率而重启撮合引擎。
  3. 按负载特征切行情推送是读多写少的广播型负载，下单是写密集。混在一起会让行情把下单的线程池吃光。
反模式

最常见的错误是按组织结构切服务 —— 每个团队一个服务。 结果是每次业务变更都要跨三个团队联调，而架构图上看起来很整齐。 边界应该跟着业务不变式走，不是跟着汇报线走。

00.4技术选型：选什么，以及更重要的是不选什么

交易系统的选型有一个特殊约束：结果必须可复现。 同样一串输入事件，重放一遍必须得到完全相同的状态。 这条约束会直接淘汰一批技术 —— 比如带随机调度的运行时、GC 停顿不可控的语言、 以及在业务层做隐式精度转换的库。

优先考虑
  • 可预测的延迟分布 —— P99 比平均值重要得多
  • 确定性的执行语义 —— 同样输入必然同样输出
  • 精确的数值类型 —— 金额绝不能用浮点
  • 成熟且被大规模验证过 —— 金融系统不做技术试验田
  • 团队真正熟悉 —— 冷门技术的隐性成本极高
明确回避
  • 把浮点数用于金额运算（0.1 + 0.2 ≠ 0.3 在账本里是灾难）
  • 核心链路上引入不确定的自动重试与随机退避
  • 为了「技术先进」而选没有生产案例的方案
  • 在撮合内核里做网络 IO 或数据库访问
  • 依赖单点且无备份方案的自研组件

用 ADR 记录决策

选型不是一次性动作。三个月后有人问「为什么当初不用 X」， 如果没有记录，就会重开一轮争论。Architecture Decision Record 用一页纸解决这个问题：

ADR · Markdown
# ADR-007：金额一律使用定点整数表示

状态：已采纳    日期：2026-03-11    决策者：交易内核组

背景
    账本需要精确的加减运算。早期原型使用 float64 表示金额，
    在压力测试中出现过 0.00000001 级别的累计误差，
    导致日终对账差异不为零。

决策
    所有金额与数量统一用 int64 表示「最小单位」，
    例如 USDT 保留 8 位小数，则 1 USDT 存为 100000000。
    币种精度由 Instrument 定义，禁止在业务代码中做隐式换算。

后果
    (+) 加减运算绝对精确，对账可以做到差异恒为 0
    (+) 序列化与哈希稳定，便于审计与重放
    (−) 乘法需谨慎处理溢出与精度截断，需封装专用类型
    (−) 前端展示需要显式格式化

替代方案
    decimal 库 —— 被否，性能不满足撮合内核对 P99 的要求。

00.5开发流程：小步、可验证、可回滚

交易系统的开发流程与普通业务系统最大的区别是： 每一次变更都要能单独回滚，且回滚不能依赖数据回滚。 因为资金数据一旦产生就不能「撤销」，只能靠补偿。 这决定了发布必须向后兼容 —— 新代码能读旧数据，旧代码也能读新数据。

  1. 变更必须小一个 PR 只做一件事。资金相关的改动尤其如此 —— 500 行的账本重构无法被有效评审，也无法被安全回滚。
  2. 评审盯三件事这个变更会不会破坏不变式（余额守恒）？失败路径有没有处理？并发下会不会有竞态？功能是否「看起来对」是次要的。
  3. CI 必须包含对账测试普通项目跑单元测试就够了。资金系统必须在 CI 里跑「随机生成一万笔操作 → 校验总额守恒」的不变量测试。
  4. 制品不可变构建产物带 commit hash，部署时只部署已构建的制品，禁止在服务器上改代码。

stages: [lint, test, invariant, build, deploy-staging]

  script: [go build -trimpath -ldflags "-X main.commit=$CI_COMMIT_SHA" -o bin/app]

00.6测试策略：五层防线

测试的价值不在于覆盖率数字，而在于在不同层次拦截不同类型的错误。 单元测试拦截逻辑错误，集成测试拦截接口不匹配，不变量测试拦截「所有测试都过了但钱还是错了」。

层次验证什么典型手段拦截的错误类型
单元测试单个函数/类的逻辑表驱动测试、边界值、竞态检测分支遗漏、边界溢出、空指针
集成测试服务与真实依赖的协作容器化依赖、真实数据库SQL 语义差异、序列化不兼容
契约测试服务间的接口约定Consumer-Driven Contracts上下游字段改名、类型漂移
不变量测试系统的全局约束属性测试、随机操作序列资金不平、订单重复成交、余额为负
混沌与压测故障与高压下的行为注入延迟/杀进程、全链路压测级联失败、雪崩、超时未设

资金系统必须有的三条不变量

这三条断言应当被写成自动化测试，在每次提交时运行：

Go · 不变量断言
// 不变量 1：总额守恒 —— 任何操作都不能凭空创造或销毁资产
func AssertConservation(before, after Snapshot) error {
    if before.Total != after.Total {
        return fmt.Errorf("资产总量变化：%d -> %d（差 %d）",
            before.Total, after.Total, after.Total-before.Total)
    }
    return nil
}

// 不变量 2：借贷平衡 —— 每笔账务的借方之和必须等于贷方之和
func AssertBalanced(e []LedgerEntry) error {
    var debit, credit int64
    for _, x := range e {
        debit += x.Debit
        credit += x.Credit
    }
    if debit != credit {
        return fmt.Errorf("借贷不平衡：借 %d ≠ 贷 %d", debit, credit)
    }
    return nil
}

// 不变量 3：余额非负 —— 可用余额与冻结余额都不允许为负
func AssertNonNegative(b Balance) error {
    if b.Available < 0 || b.Frozen < 0 || b.Locked < 0 {
        return fmt.Errorf("出现负余额：可用 %d 冻结 %d 锁定 %d",
            b.Available, b.Frozen, b.Locked)
    }
    return nil
}
本章要点 01

这三条不变量是整站的技术主线。第 03 章讲它们在撮合里怎么被维持， 第 04 章讲账本怎么用复式记账从结构上保证它们， 第 05 章讲当它们真的被打破时，系统靠什么发现并止损。

00.7上线与运维：把「我不知道」变成「我能看见」

上线不是终点，是系统第一次面对真实流量。运维的核心目标只有一个： 缩短从「出问题」到「知道出问题了」之间的时间。 这个时间叫 MTTD（Mean Time To Detect），它比 MTTR 更值得投入 —— 因为你无法修复一个你还不知道存在的故障。

可观测性的三个支柱

  • 指标Metrics —— 聚合的数值时间序列。下单 QPS、撮合延迟分位、订单簿深度、各币种余额总量。适合做告警与趋势判断，成本低、保留久。
  • 日志Logs —— 离散的事件记录。必须结构化（JSON），必须带 trace_id 与 order_id，否则在故障时毫无用处。资金相关日志需要单独隔离并长期留存。
  • 追踪Traces —— 一次请求跨服务的完整调用链。定位「慢在哪一跳」的唯一有效手段。对交易系统而言，一笔订单的全链路追踪是必备能力。

用 SLO 而不是「尽力而为」

SLO（服务等级目标）把「要稳定」翻译成一个可计算的数字， 并由此推出错误预算：一个月允许失败多少次。 错误预算的意义在于它让「发布新功能」和「保持稳定」不再是吵架， 而是一个算术问题 —— 预算还有，就继续发；预算烧完了，就停下修稳定性。

00.8迭代：让系统可以长期活着

一个交易系统上线只是开始。它会在未来几年里持续面对新币种、新业务线、 新监管要求和新的攻击手法。能不能活下来，取决于架构是否留了演进空间。

技术债要分类，不能笼统地「还」

  • 有息债 —— 每次改需求都要额外付出的成本。例如把费率硬编码在撮合里。这类债必须尽快还，因为它每天都在收利息。
  • 无息债 —— 不影响后续开发，只是不够优雅。例如某个工具类命名不好。可以一直挂着，不必焦虑。
  • 致命债 —— 平时不显形，一旦触发就造成资金损失的隐患。例如用浮点算金额、用时间戳做幂等键。这类债不是「要不要还」的问题，是「必须立刻停下手上的活去还」。

重构的安全姿势

资金系统的重构有一条铁律：先建立可对比的基准，再动代码。 具体做法是影子运行 —— 新逻辑与旧逻辑并行跑，用真实流量比对两边输出， 差异为零一段时间后才切换。

  1. 埋点与基准在旧逻辑出口记录输入与输出，形成可回放的样本集。
  2. 影子运行新逻辑接同样的输入，输出只记录不生效，与旧逻辑逐笔比对。
  3. 差异归零差异必须为零。任何差异都是发现隐藏 bug 的机会，逐条查清原因。
  4. 灰度切流按用户或交易对逐步切换，每档观察至少一个完整对账周期。
  5. 清理旧码确认新逻辑稳定后再删旧代码。留一条随时可退的路，直到确认不需要为止。
第 00 章 · 检查清单

在写第一行代码之前，确认这几件事已经有答案：
① 每条需求都能写出验收标准与失败判据；
② 核心实体的状态机已被显式建模，非法迁移会失败；
③ 架构的依赖方向单向向下，领域核心不依赖具体存储；
④ 金额使用定点整数，选型决策有 ADR 记录；
⑤ CI 里跑着资金不变量测试；
⑥ 每个关键指标都有 SLO，且定义了错误预算；
⑦ 重构有影子运行与灰度切流的具体计划。
