交易链核心：撮合是怎么发生的

这是整站最硬的一章。我们会把订单从进入系统到变成成交记录的每一步拆开， 看清楚订单簿用什么数据结构、撮合算法怎么写、为什么必须单线程， 以及「价格优先、时间优先」这八个字在代码里到底是什么。

一笔订单如何被撮合，为什么结果必须可复现
关键产出

03.1订单的完整生命周期

一笔订单从诞生到消亡，会经过若干个状态。这些状态不是装饰， 每一个都对应着资金的不同归属。理解这一点， 就理解了为什么状态机不能随意简化。

图 03-A 订单状态机。PENDING_NEW 是一个容易被忽视但极其危险的状态：此时资金尚未冻结，如果它持续太久（比如因为下游阻塞），用户就能用同一笔钱下第二单。因此这个状态的停留时间应当被监控并设告警。

冻结额随成交递减：一个必须精确的账

假设用户下买单：价格 43200，数量 1 BTC，冻结 43200 USDT。 成交 0.4 BTC 后，冻结额应该变成多少？

伪代码 · 冻结额维护
// 下单时冻结（买单冻结计价币，卖单冻结基础币）
frozen_amount = price * qty                    // 43200 * 1 = 43200

// 每次成交后，按「成交量对应的冻结额」解冻并划转
// 注意：必须用「累计成交额」相减，而不是「每笔成交额」累加
// —— 后者会因精度截断产生累积误差
released = round_down(price * cum_filled_qty, quote_precision)
remaining_frozen = frozen_amount - released

// 示例：成交 0.4 BTC（累计），价格 43200
// released = 43200 * 0.4 = 17280
// remaining_frozen = 43200 - 17280 = 25920
// 若第二笔再成交 0.6 BTC：
// released = 43200 * 1.0 = 43200 → remaining_frozen = 0  ✓ 恰好归零

// 若改用「每笔累加」：17280 + round_down(43200*0.6) = 17280 + 25920 = 43200 ✓
// 看似也对 —— 但当价格带小数、数量精度更高时，逐笔累加会出现 0.00000001 级偏差，
// 最终导致「订单已完全成交但冻结额还剩 1 个最小单位」的脏数据。
// 用累计值相减是幂等的、可重放的，逐笔累加不是。
不变量

订单进入终态时，其冻结额必须精确归零。 这个不变量应当被写成断言，在每一笔状态迁移后校验。 违反它意味着有资金被永久锁死 —— 用户看得见余额却用不了， 这类问题在客服侧表现为「我的钱不见了」，而实际上它只是被冻结着。

03.2订单簿：数据结构决定性能上限

订单簿要回答两个高频问题：当前最优买价/卖价是多少、 某个价位的挂单队列里谁排在前面。 数据结构的选型直接决定了这两个问题的答案要多快。

结构找最优价插入/删除是否实用说明
有序数组O(1) 取首尾O(n) 移动元素勉强可用价位数量有限（通常几百档）时，内存移动的实际开销可以接受
红黑树 / 跳表O(log n)O(log n)通用方案价位动态变化大时的稳妥选择，实现复杂度中等
价格档位数组O(1) 索引O(1)最优价格按最小变动单位离散化后用数组下标寻址，需要处理价格范围
哈希表 + 双向链表—O(1)辅助结构用于 O(1) 定位并撤销任意订单，通常与其他结构组合使用

一个可用的订单簿结构

实践中常见的组合是：价位用有序结构维护，同价位内用 FIFO 队列。 下面是一个精简但完整的实现，重点是数据结构的选择与不变式：

Go · 订单簿
type OrderBook struct {
    Symbol    string
    Bids      *PriceLevels          // 买盘：价格从高到低
    Asks      *PriceLevels          // 卖盘：价格从低到高
    Index     map[OrderID]*Order   // O(1) 定位订单，用于撤单
    Seq       uint64              // 全局递增序列号
}

// 一个价位：价格 + 该价位所有订单的 FIFO 队列
type PriceLevel struct {
    Price     int64       // 定点整数表示，避免浮点误差
    TotalQty  int64       // 该价位总量（冗余字段，用于 O(1) 算深度）
    Orders    []*Order    // 严格按到达顺序排列 —— 时间优先的物理载体
}

// 插入限价单
func (b *OrderBook) Insert(o *Order) {
    o.Seq = b.nextSeq()                    // 序列号在此刻确定，这就是「时间」
    side := b.sideOf(o)
    lvl := side.GetOrCreate(o.Price)
    lvl.Orders = append(lvl.Orders, o)     // 追加到队尾 = 时间优先
    lvl.TotalQty += o.RemainingQty
    b.Index[o.ID] = o
}

// 撤单：必须是 O(1)，因为行情剧烈时撤单量会暴涨
func (b *OrderBook) Cancel(id OrderID) (*Order, bool) {
    o, ok := b.Index[id]
    if !ok { return nil, false }
    lvl := b.sideOf(o).Get(o.Price)
    lvl.remove(o)                          // 从队列中摘除并更新 TotalQty
    delete(b.Index, id)
    if lvl.Empty() { b.sideOf(o).Delete(o.Price) }
    return o, true
}
为什么需要 Index

没有 Index，撤单就要遍历整个订单簿找到那个订单 —— 在行情剧烈波动时，撤单请求会暴涨，遍历会直接拖垮撮合线程。 用一点内存换 O(1) 的撤单能力，是订单簿设计里最划算的交易。

03.3「价格优先、时间优先」到底是什么

这八个字每个人都会背，但落到代码里有几个容易含糊的点。精确的定义是：

  1. 价格优先买单出价高的先成交，卖单要价低的先成交。这一条决定「先看哪个价位」。
  2. 时间优先同一价位内，先到达的先成交。这一条决定「同一价位里先看哪个订单」。
  3. 「时间」指的是系统接收时间不是客户端发起时间，也不是服务器处理时间。它必须是由定序器分配的单调整体序列号。用本地时钟会产生不可复现的结果。
  4. 成交价取被动方价格这一点常被误解。买单以 43300 吃卖盘，卖盘最优价是 43200，则成交价为 43200（挂单方价格），不是 43300。主动方获得了价格改善。

图 03-B 一次撮合的完整过程。买单出价 43205 高于卖一 43202，立即成交；成交价取被动方（卖单）的价格 43202。这不是细节，而是决定了「谁获得价格改善」的规则，也是所有交易规则文档里必须写清的一条。

03.4撮合算法：主循环只有二十行

撮合的核心逻辑出奇地短。复杂的是围绕它的工程细节 —— 精度、幂等、事件产出、异常处理。但主循环本身可以写得很清楚：

Go · 撮合主循环
// Match 撮合一笔新到达的订单，返回产生的所有成交
func (b *OrderBook) Match(taker *Order) []Trade {
    var trades []Trade

    for taker.RemainingQty > 0 {
        // 1. 取对手方最优价位；没有对手盘则挂单等待
        maker, ok := b.bestOpposite(taker.Side)
        if !ok { break }

        // 2. 价格是否可成交？不可成交则挂单等待
        //    买单：对手卖价 <= 我的出价     卖单：对手买价 >= 我的要价
        if !b.crossable(taker, maker) { break }

        // 3. 取该价位队首订单（时间优先）
        head := maker.Orders[0]

        // 4. 成交量 = 双方剩余量的较小值
        qty := min(taker.RemainingQty, head.RemainingQty)

        // 5. 成交价 = 被动方价格（挂单方价格）
        price := head.Price

        // 6. 更新双方剩余量
        taker.RemainingQty -= qty
        head.RemainingQty  -= qty
        maker.TotalQty     -= qty

        // 7. 产出成交事件（注意：这里不写数据库，只产出事件）
        trades = append(trades, Trade{
            Symbol:   b.Symbol,
            Price:    price,
            Qty:      qty,
            TakerID:  taker.ID,
            MakerID:  head.ID,
            Seq:      b.nextSeq(),
        })

        // 8. 挂单方完全成交则出队
        if head.RemainingQty == 0 {
            maker.removeHead()
            delete(b.Index, head.ID)
            if maker.Empty() { b.sideOf(head).Delete(head.Price) }
        }
    }

    // 9. 主动方未完全成交 → 剩余部分挂入订单簿
    if taker.RemainingQty > 0 {
        b.Insert(taker)
    }
    return trades
}

注意第 7 步的那句注释。这是撮合引擎设计里最重要的一条纪律：

纪律

撮合内核不写数据库，不读数据库，不做任何 IO。 它只做一件事：接收有序事件，产出结果事件。 持久化、通知、统计、对账，全部由下游消费者完成。 这条纪律让撮合内核保持在纯内存、纯计算的状态 —— 这也是它能做到微秒级延迟的根本原因。

03.5为什么撮合必须单线程

这是新手最常提出的质疑：「现在都是多核时代了，为什么不用多线程？」 答案不是「性能不够」，而是正确性要求。

并发撮合会导致不可复现

设想两个线程同时处理 BTC/USDT 的两个买单。它们的执行顺序取决于 操作系统的调度、锁的竞争、缓存一致性协议 —— 这些都是非确定的。 于是同样的输入，两次运行会得到不同的成交结果。

后果是连锁的：

  • 无法审计 —— 用户质疑「为什么我的订单没成交」，你无法复现当时的情况。
  • 无法灾备 —— 主节点故障后，备节点重放事件流会得到不同的状态，两边账本对不上。
  • 无法回溯 —— 出现资金差异时，无法通过重放定位是哪一笔开始错的。
多线程撮合
  • 吞吐可能更高，但结果不可复现
  • 需要复杂的锁协议，锁竞争本身成为瓶颈
  • 无法通过重放验证状态一致性
  • 灾备切换后两边状态可能不一致
  • 故障排查变成玄学
单线程 + 分片
  • 结果完全确定，可重放、可审计、可灾备
  • 无锁，无上下文切换，CPU 缓存友好
  • 单分片性能可达数十万笔/秒
  • 横向扩展靠增加交易对分片
  • 故障排查可以精确到具体序列号

单线程为什么还能这么快

「单线程」听起来很慢，但现代 CPU 的单核性能远超直觉。 一个优化良好的撮合内核，处理一笔订单通常在几百纳秒到几微秒之间。 按 2 微秒算，单线程每秒可以处理 50 万笔订单 —— 这已经超过绝大多数交易对的实际峰值需求。

能这么快，靠的是消除一切非必要开销：

  • 零分配对象池复用。撮合循环里不产生垃圾，避免 GC 停顿。所有订单对象从预分配池中取出、归还。
  • 零拷贝事件直接写入环形缓冲。不与下游做内存拷贝，下游通过共享内存读取。
  • 零系统调用不做 IO、不加锁、不记录日志。这些动作全部挪到其他线程。
  • CPU 亲和绑定核心 + 关闭超线程。避免撮合线程被调度到其他核心导致缓存失效。

03.6定序：把并发压成一个确定的序列

既然撮合必须串行，那并发的请求就得在进入撮合之前被排成一队。 完成这个动作的组件叫定序器（Sequencer）。它是整个系统里 唯一的顺序裁定者。

图 03-C 定序器的作用。注意 X、Y、Z、W 的最终顺序（X→Z→Y→W）与它们到达网关的物理顺序无关 —— 重要的是定序器裁定了一个唯一顺序，并且所有下游都看到同一个顺序。这就是「确定性」的来源。

定序器自身的高可用

定序器是单点，但它不能是单机。标准做法是 主备 + 多数派确认：主节点分配序列号后， 必须得到多数派副本的确认才向客户端返回「已受理」。 主节点故障时，备节点从最后一条已确认的序列号继续，不会丢也不会重复。

与共识算法的关系

这套机制与 Raft / Paxos 类共识算法解决的是同一个问题： 在不可靠的网络上达成一个可靠的顺序。区别在于交易系统的定序器 通常只负责「排序」这一件事，把状态机复制交给下游消费者， 从而获得更高的吞吐。

03.7从成交到结算：事件如何驱动一切

撮合产出的 Trade 事件只是开始。它要被若干个消费者分别处理， 每个消费者做一件独立的事。这种事件驱动的结构， 是交易系统能在保证一致性的同时保持低延迟的关键。

消费者消费什么产出什么失败影响
结算器Trade 事件解冻、划转、账本条目严重 —— 必须优先保证
行情服务Trade + 订单簿变更盘口增量、最新成交、K 线中等 —— 可重放恢复
订单服务Trade + 状态变更更新订单状态、推送用户回报中等 —— 可重放
风控服务全量事件风险指标、异常检测低 —— 可延迟
数据仓库全量事件成交历史、统计分析低 —— 可批量补

消费必须幂等

消息队列通常保证「至少一次」投递，意味着同一条事件可能被消费两次。 如果结算器不幂等，同一笔成交会被扣两次钱。 解决办法是用序列号做幂等键：

Go · 幂等消费
// 每条账本条目都携带产生它的 (seq, event_type)，构成唯一键
type LedgerEntry struct {
    Seq       uint64   // 来源事件序列号
    EventType string   // TRADE / FEE / DUST / FUNDING ...
    EntryNo   int      // 同一事件内的条目序号（一笔成交产生多条）
    AccountID string
    Asset     string
    Debit     int64
    Credit    int64
}

// 数据库层用唯一约束兜底 —— 比应用层判断更可靠
// UNIQUE KEY uk_ledger (seq, event_type, entry_no)

func (s *Settler) Apply(e LedgerEntry) error {
    // INSERT ... ON CONFLICT DO NOTHING
    // 重复消费时唯一约束直接拦下，不产生任何副作用
    n, err := s.db.InsertIgnore(e)
    if err != nil { return err }
    if n == 0 {
        s.metrics.DuplicateConsumed.Inc()   // 记录但不报错 —— 这是正常情况
    }
    return nil
}
为什么唯一约束比应用层判断可靠

应用层用「先查再写」实现幂等，在并发下会有竞态窗口： 两个线程同时查询，都发现不存在，然后都写入。 数据库的唯一约束是原子的，它由存储引擎保证， 不依赖应用代码的正确性。把幂等性下沉到存储层， 是资金系统的一条通用经验。

03.8行情分发：把撮合结果变成可消费的数据流

行情是交易系统的「广播电台」：一个生产者，数万个消费者， 且每个消费者都希望尽快拿到最新数据。这决定了它必须采用 与交易链路完全不同的技术方案。

  • 盘口增量推送 + 序列号。只推变化的价位，客户端按序列号应用。丢包即重连拉快照。
  • 成交逐笔推送。最新成交是用户最关注的信息，必须实时。通常会做合并（同一价位短时间内的成交合并推送）以降低带宽。
  • K 线服务端聚合。由成交数据按时间窗口聚合而成。关键点是「当前未收盘的 K 线」要持续更新，收盘后固化。多周期（1m/5m/1h/1d）由不同消费者并行聚合。
  • 标记价独立计算。合约用的标记价格来自多个现货市场的加权，不是最新成交价。它必须由独立服务计算并广播，不能由撮合产出。
常见故障

行情堆积。当行情推送速度超过客户端消费速度时， 服务端的发送缓冲区会堆积，最终导致内存暴涨或连接被强制断开。 正确做法是丢弃旧数据而不是排队 —— 对行情而言，最新的一个盘口快照永远比一百个过期的增量更有价值。 这需要为每个连接维护「只保留最新状态」的合并缓冲区。

03.9交易链的一致性保证：一张完整的清单

把本章讲的所有机制收拢成一张清单。这些是「交易链不会出错」的 具体技术保证，每一条都可以在代码或架构里找到对应物。

GUARANTEE 01

确定性撮合

单线程 + 全内存 + 无 IO。相同输入序列必然产生相同输出，支持重放验证与灾备切换。

GUARANTEE 02

全局有序

由定序器分配单调递增序列号，所有下游看到同一顺序。序列号是幂等键与审计线索。

GUARANTEE 03

先冻结后撮合

资金校验与冻结在进入撮合之前完成，杜绝「成交了但钱不够」的不可逆局面。

GUARANTEE 04

终态零冻结

订单进入终态时冻结额必须精确归零，通过断言校验，避免资金被永久锁死。

GUARANTEE 05

累计而非累加

解冻金额按「累计成交量」计算，而非逐笔累加，消除精度截断的累积误差。

GUARANTEE 06

幂等消费

用 (seq, event_type, entry_no) 唯一约束保证重复消费无副作用，兜底放在数据库层。

GUARANTEE 07

成交必成对

一笔 Trade 必然同时归属买卖两个订单，双方数量变化绝对值相等。这是撮合的结构性不变量。

GUARANTEE 08

主链路无 IO

持久化、通知、统计全部异步。主链路只做必要动作，保证延迟可控且不被下游拖垮。

第 03 章 · 检查清单

① 订单状态机显式建模，终态零冻结有断言；
② 订单簿有 O(1) 撤单索引，同价位严格 FIFO；
③ 「时间」由定序器序列号定义，不用本地时钟；
④ 成交价取被动方价格，并写入规则文档；
⑤ 撮合内核无 IO、无锁、无分配；
⑥ 定序器主备 + 多数派确认，不丢不重；
⑦ 所有事件消费者幂等，唯一约束在存储层兜底；
⑧ 行情用增量 + 序列号，堆积时丢旧不排队。
