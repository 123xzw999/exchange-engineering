业务全景：交易所到底在做什么

在讨论架构之前，先得知道系统要支撑哪些业务。这些业务表面上五花八门， 底层却共用同一套资金骨架 —— 理解这一点，才能理解为什么架构可以既复杂又统一。

01.1业务地图：一条业务线的复杂度由什么决定

判断一条业务线难不难做，别看它的界面有多花哨，看三个问题： 资金关系是否跨账户、是否引入时间维度上的负债、 风险敞口由谁承担。三个问题答完，复杂度基本就定了。

业务线资金关系是否产生负债风险承担方工程复杂度
现货交易同账户内两币种互换否用户中
杠杆借币跨账户，含利息计提是（借出方债权）平台 + 用户高
永续合约保证金账户，含资金费划转是（对手方敞口）平台承担穿仓很高
理财产品资金从交易账户划入理财账户是（应付收益）平台中
法币通道链下法币与链上资产的兑换是（待结算头寸）平台 + 商户高（合规重）
充提币链上 ↔ 平台内部账本否（托管）平台（托管责任）很高（安全重）
核心判断

真正把复杂度拉高的，是「负债」与「托管」这两个词。 现货交易只是用户自己账户内的资产互换，平台不欠任何人钱； 而一旦引入杠杆、合约、理财，平台账上就出现了「我欠用户多少」这个概念， 所有关于准备金的难题随之而来。充值提现则引入另一类责任：用户把资产交给你保管。

01.2现货交易：最基础的一层

现货是所有业务的原子。用户用 A 币换 B 币，交易完成即交割，没有未来义务。 它的资金关系干净到可以一句话说清： 买方账户的计价币减少、基础币增加；卖方相反；两边变动量相等。

但「简单」只体现在资金关系上。工程上它已经需要：

  • 撮合价格优先、时间优先的连续竞价。要在微秒级决定哪两笔订单成交、以什么价格成交、成交多少量。
  • 冻结下单即冻结资金。挂单期间资产被锁住，不能再用于其他订单。冻结粒度必须精确到「这一笔订单占用了多少」。
  • 精度价格与数量的精度约束。BTC/USDT 价格可能保留 2 位小数、数量保留 6 位。成交金额按精度截断后，剩余的零头归属必须明确，否则对账必然出现尾差。
  • 费率阶梯费率与返佣。同一笔成交，买卖双方费率可能不同，还要考虑邀请返佣的二级分润。

精度的尾差问题

这是现货系统里最容易被忽略、又必然踩到的坑。举例：数量 0.12345678 BTC， 价格 43210.55 USDT，乘积是 5334.2359... USDT。 如果计价币精度只到 0.01，截断后是 5334.23，那 0.0059 去哪了？

伪代码 · 尾差处理
// 成交金额必须用一个明确定义的舍入方向，且零头有归属
quote_amount = round_down(price * qty, quote_precision)

// 尾差 = 理论值 - 实付值，必须记账，不能丢弃
dust = price * qty - quote_amount

// 两种可接受的处理方式（必须二选一并写进规范）：
// 方式 A：尾差归平台手续费账户（平台承担，用户不吃亏）
// 方式 B：尾差从卖方所得中扣除（卖方承担，需在费率说明中披露）
// 无论选哪种，dust 都必须产生一条账本条目 ——
// 「消失的零头」是对账差异最常见的来源
ledger.append(DustEntry{amount: dust, to: FEE_ACCOUNT})
血泪教训

很多系统的对账差异在运行几个月后才被发现，金额小到没人注意， 但累计起来是一笔真实的资金缺口。更麻烦的是，当你想回溯是哪一笔产生的， 日志里已经找不到痕迹 —— 因为当初根本没记。 凡是金额被「截断」「取整」「换算」的地方，都必须产生账本条目。

01.3杠杆与借贷：平台第一次开始「欠钱」

杠杆的机制是：用户抵押一部分资产，借入另一部分资产去交易，放大收益与亏损。 技术上是三件事的叠加 —— 借贷、计息、强平。

  1. 借贷资金从「借贷池」划到用户账户，同时在用户账户记一笔负债。这一刻起，平台账上出现了「用户欠我多少」和「我欠出借方多少」两条记录 —— 这就是负债的引入。
  2. 计息利息按小时或按秒计提。这里有个工程陷阱：计息必须可重放。如果计息逻辑依赖「当前时间」，重放历史时会算出不同的结果。正确做法是用事件时间，且每次计息产生独立的账本条目。
  3. 强平当风险率低于阈值时，系统自动平仓。这是全系统最危险的操作之一 —— 它在下单，而且是在市场剧烈波动、系统负载最高的时候下单。
强平的工程风险

强平引擎必须能在极端行情下工作：此时行情推送量是平时的几十倍、 用户撤单请求暴涨、网络可能拥塞。如果强平引擎和普通下单走同一条路径， 它会因为排队而错过最佳平仓时机，导致穿仓（亏损超过保证金）。 实践中强平通常走独立的、有优先级的通道，甚至直接对接撮合内核的紧急接口。

01.4合约：把风险敞口做成一个显式对象

合约交易不交换资产本身，只交换「价格变动带来的盈亏」。 这个抽象带来一个关键设计：持仓（Position）必须成为一个独立的一等公民， 而不再是余额的附属品。

U 本位合约
  • 保证金与盈亏都用稳定币计价，账本结构简单
  • 盈亏计算直观：(平仓价 − 开仓价) × 数量 × 方向
  • 风险：稳定币本身也有脱锚风险
  • 工程重点在保证金率与强平队列
币本位合约
  • 保证金与盈亏用标的币计价，出现「非线性盈亏」
  • 盈亏公式含倒数项，浮点与精度问题成倍放大
  • 同样的仓位，不同价格下的盈亏不是线性关系
  • 工程重点在数值稳定性与舍入一致性

资金费：一个每 8 小时发生的资金划转

永续合约没有到期日，靠资金费把合约价格锚定在现货价格附近。 每过一个结算周期，多头与空头之间按持仓量划转一笔资金。 它的工程特点很鲜明：

  • 批量、定时、必须原子 —— 一次结算可能涉及几十万个持仓。要么全部成功，要么全部回滚，不能出现「一半人扣了、一半人没扣」。
  • 金额可能为负 —— 多空方向由资金费率符号决定，代码必须同时处理两种流向。
  • 必须可重放 —— 结算结果依赖当时的标记价格与持仓快照，这些必须落库，否则无法审计。

01.5理财与质押：把用户资产变成平台的负债

理财产品在技术上是一份带时间约束的负债合约： 用户把资产划入理财账户，平台承诺在到期日归还本金加收益。 它在账本上产生的条目与现货完全不同 —— 现货是「资产互换」，理财是「资产转移 + 负债确认」。

图 01-A 理财业务的资金流与负债流是两条独立记录。用户看到的「我的理财余额」是债权，而平台账上对应的资产已经被运用出去了 —— 这两者之间的差额，就是平台的真实风险敞口。

01.6法币通道与 C2C：链下世界与链上账本的对接

法币入金是最容易出事、也最容易被低估的环节。它要处理一个本质矛盾： 法币的转移发生在银行体系里，无法与链上账本原子化。 银行转账可能延迟、可能撤回、可能因为风控被冻结。

C2C（用户对用户）模式把这个矛盾转移给了商户，平台只做托管与仲裁：

  1. 卖方挂单卖方将数字资产划入平台托管账户，资产从「可用」变为「托管冻结」。这一步必须是原子的，否则会出现「挂了单但没锁币」。
  2. 买方付款买方在链下完成银行转账，然后在平台标记「已付款」。平台此时不能直接放币 —— 因为银行转账可能并未真正到账。
  3. 卖方确认卖方核实收款后点击放币，托管资产划转给买方。这一步是最终结算点。
  4. 争议仲裁若卖方不确认或买方未付款，进入客服仲裁流程。技术上的要求是：所有证据（付款凭证、时间戳、聊天记录）必须完整留存且不可篡改。
工程要点

这类业务的技术核心不是高并发，而是状态机的严谨与证据链的完整。 一个「订单」在这里有十几个状态，每个状态迁移都对应真实世界的资金动作， 任何一步可被跳过都会造成损失。它和撮合引擎是两种完全不同的工程能力。

讲了六条业务线，现在把它们收拢。无论业务形态如何变化， 底层的资金骨架始终是这四层：

图 01-B 四层骨架。业务层可以不断增加新产品，但账本层永远是唯一的资金事实来源。任何业务线都不允许绕过账本直接改余额 —— 这是整个系统最重要的一条纪律，第 04 章会展开。

第 01 章 · 检查清单

① 每条业务线都明确了「是否产生负债」「谁承担风险」；
② 所有金额截断、取整、换算的位置都有账本条目，不存在「消失的零头」；
③ 计息与结算逻辑基于事件时间而非系统时间，可重放；
④ 强平/清算走独立通道，不与普通下单竞争资源；
⑤ 法币类业务有完整的状态机与不可篡改的证据链；
⑥ 业务层不允许绕过账本层直接修改余额。
