账本与清结算：钱是怎么被记下来的

撮合决定了「谁跟谁成交」，账本决定了「钱从谁那里到谁那里」。 这一章讲的是资金系统里最不容出错的部分 —— 余额为什么必须拆成三个数、复式记账为什么能防住绝大多数资金事故、 以及「可用」和「可提」之间那道必须存在的墙。

04.1余额为什么必须拆成三个数

新手设计的第一版余额通常是一个字段：balance = 1000。 这个设计在第一次下单时就会崩掉 —— 因为系统无法回答 「这 1000 里有多少正在被挂单占用」。

正确的模型是把余额拆成三个分量：

图 04-A 余额三态。冻结不是扣款，它是同一笔钱从「可支配」变成「被占用」。这个区分极其重要：如果把冻结实现成扣款，撤单时就要「退款」，一旦退款失败，钱就真的丢了；而如果冻结只是状态转移，撤单只需把它搬回去，失败也可以重试。

错误实现
  • 下单时直接 balance -= amount
  • 撤单时 balance += amount 作为补偿
  • 冻结额没有独立记录，无法回答「这钱为什么动不了」
  • 撤单失败 = 用户资金丢失，只能人工补
  • 并发下同一笔钱可能被两笔订单占用
正确实现
  • 下单时 available -= amount; frozen += amount（同一事务）
  • 撤单时反向搬运，幂等且可重试
  • 冻结额可按订单维度查询，客服能直接回答用户
  • 冻结操作天然防重：可用余额不足即拒绝
  • 任何时刻 Total 不变，资金守恒可验证

04.2复式记账：让账本自己证明自己

复式记账是五百年前意大利商人发明的技术，至今仍是所有金融系统的基石。 它的核心规则只有一条：每一笔交易至少涉及两个账户，且借方总额恒等于贷方总额。

这条规则带来的最大好处是：账本可以自我验证。 如果某一笔记错了，借贷平衡立刻被打破，系统能在第一时间发现异常， 而不是等到用户投诉。

一笔现货成交的完整账本条目

用户在 BTC/USDT 市场用 43200 USDT 买入 1 BTC，手续费 0.1%（以 BTC 计）。 这笔业务会产生四条账本条目：

图 04-B 一笔成交产生六条条目，按币种分别借贷平衡。BTC 侧：进 0.999 + 手续费 0.001 = 出 1.0 ✓；USDT 侧：买方出 43200 = 卖方进 43200 ✓。任何一侧不平，系统立刻知道出了问题。

为什么这比「直接改余额」强

直接改余额只留下「结果」，不留下「原因」。当余额对不上时， 你只能看到一个数字错了，无法回答「哪一步导致的」。 复式记账让每一分钱的移动都有来源与去向， 并且自带校验 —— 这就是账本能自我证明的含义。

账本表的结构

SQL · 账本表
CREATE TABLE ledger_entry (
    id            BIGINT      NOT NULL AUTO_INCREMENT,
    entry_no      BIGINT      NOT NULL,          -- 全局单调递增，账本内的绝对顺序
    biz_type      VARCHAR(32) NOT NULL,          -- TRADE / DEPOSIT / WITHDRAW / FEE / FUNDING
    biz_id        VARCHAR(64) NOT NULL,          -- 业务单号（成交号 / 提现单号）
    seq           BIGINT      NOT NULL,          -- 来源事件序列号（幂等键组成部分）
    account_id    VARCHAR(64) NOT NULL,
    user_id       VARCHAR(64) NOT NULL,
    asset         VARCHAR(16) NOT NULL,          -- 币种
    direction     TINYINT     NOT NULL,          -- 1=借 DEBIT  -1=贷 CREDIT
    amount        BIGINT      NOT NULL,          -- 最小单位的整数，永远为正
    balance_after BIGINT      NOT NULL,          -- 变动后余额，便于逐笔核对
    created_at    DATETIME(3) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_idem (seq, biz_type, entry_no), -- 幂等：重复写入直接被拦
    KEY idx_user_asset (user_id, asset, entry_no),  -- 用户流水分页
    KEY idx_biz (biz_id)                             -- 按业务单号追溯
) ENGINE=InnoDB;

-- 关键约束：账本表禁止 UPDATE 和 DELETE
-- 通过数据库权限控制：应用账号只有 INSERT 与 SELECT 权限
-- 任何修正都通过追加「冲正条目」实现，而不是修改历史
GRANT INSERT, SELECT ON exchange.ledger_entry TO 'app'@'%';
balance_after 的价值

冗余存储「变动后余额」看起来违反范式，但它带来两个关键能力： ① 逐笔核对 —— 每条记录都能独立验证 上一条的 balance_after ± amount = 本条的 balance_after； ② 快速定位 —— 对账出现差异时，可以用二分查找 快速定位到第一条不平的记录，而不用从头重算全部流水。

04.3冻结与解冻的完整生命周期

冻结看起来简单，但在「部分成交 + 撤单 + 并发」的组合下， 有几种边界情况很容易写错。下面把一笔订单的完整资金轨迹画出来。

图 04-C 冻结的生命周期。第 ② 步与第 ③ 步释放的金额必须精确加总为初始冻结额。用「累计成交量」计算释放额（见第 03 章）是保证这一点的唯一可靠方法。

并发下的经典 bug

「部分成交」与「用户撤单」可能同时到达。如果不加控制， 可能出现：撤单逻辑读到「剩余 0.6 BTC」并释放了 25920， 而同时成交逻辑也在处理一笔 0.6 BTC 的成交并释放 25920 —— 两笔都执行，用户凭空多出 25920 USDT。

解决办法是让所有影响同一订单的操作都在定序器排队。 撤单和成交都变成有序事件，由单线程依次处理。 这样「读到的剩余量」永远是最新的，不可能重复释放。 这正是第 03 章强调「全局有序」的价值所在 —— 它不只服务于撮合，也服务于资金安全。

04.4逐笔结算：为什么不能批量算

一个自然的想法是：把一段时间内的成交攒起来，最后统一结算， 这样能减少数据库写入。这个想法在资金系统里是危险的。

逐笔结算
  • 每一笔成交立即产生账本条目，状态实时准确
  • 故障时最多丢失一笔，影响面可控
  • 用户可以实时看到余额变化
  • 对账可以随时进行，不必等批处理窗口
批量结算
  • 批处理窗口内余额是「旧的」，用户看到的是过期数据
  • 批处理失败时要重算整批，回滚代价极高
  • 无法定位差异来自哪一笔
  • 窗口末期积压，容易引发雪崩

逐笔结算的性能问题可以靠批量提交解决 —— 注意这是「批量写数据库」，而不是「批量算资金」。 资金的计算仍然逐笔进行，只是把多条 INSERT 合并成一个事务提交，减少磁盘同步次数。

Go · 批量提交但逐笔计算
// 结算器：从事件流读取成交，逐笔计算资金变动
func (s *Settler) Run() {
    batch := make([]LedgerEntry, 0, 256)
    ticker := time.NewTicker(5 * time.Millisecond)  // 5ms 或攒够 256 条就提交

    for {
        select {
        case ev := <-s.events:
            // 逐笔计算 —— 资金逻辑绝不合并
            entries := s.calcEntries(ev)
            batch = append(batch, entries...)
            if len(batch) >= 256 {
                s.flush(batch); batch = batch[:0]
            }
        case <-ticker.C:
            // 批量提交 —— 只影响写入效率，不影响资金语义
            if len(batch) > 0 { s.flush(batch); batch = batch[:0] }
        }
    }
}

// flush 在一个事务内写入，保证「要么全成，要么全不成」
func (s *Settler) flush(batch []LedgerEntry) {
    s.db.Transaction(func(tx *Tx) error {
        for _, e := range batch {
            if err := tx.InsertIgnore(e); err != nil { return err }
        }
        return tx.UpdateBalances(batch)   // 余额在同一事务内更新
    })
}

04.5「可用」与「可提」：一道必须存在的墙

用户看到的余额里有 10000 USDT，但点提现时却只能提 8000。 这不是 bug，而是一道精心设计的墙。原因有三：

  1. 未结算资金法币入金可能还没真正到账（银行转账存在延迟与撤回），但平台已经给用户记了账。这部分钱可以交易，不能提走。
  2. 风控限额用户当日提现额度已用、账户风险等级受限、或触发了人工审核。这些是策略性的限制。
  3. 流动性保护平台的热钱包余额有限。如果所有用户同时提现，热钱包会被掏空。设置可提额度是一种缓冲，给冷钱包补充留出时间窗口。
工程实现

「可提」通常是计算出来的，而不是存储的： 可提 = 可用 − 当日已提 − 冻结中的提现申请 − 风控保留额。 把它做成派生值而非独立字段，可以避免「忘记同步」导致的脏数据。

04.6手续费、资金费与返佣的记账

这些「附加资金流」是最容易记错的地方，因为它们金额小、频率高、 且往往涉及多方分润。原则只有一条：每一笔都必须是完整的复式分录。

类型资金流向记账要点
交易手续费 用户 → 平台手续费账户 按成交额与费率计算，注意币种（可能用计价币也可能用基础币），且必须与成交在同一事务
邀请返佣 平台手续费账户 → 邀请人账户 按比例拆分，可能多级。必须在手续费入账后立即计算，否则会漏
资金费 多头账户 ↔ 空头账户 总额守恒（一方付出等于另一方收取），平台不参与。批量结算时必须原子
借贷利息 借款人账户 → 出借人账户 + 平台利息账户 按时间计提，必须可重放。利率变更要分段计算，不能整体重算
提现手续费 用户账户 → 平台手续费账户 在提现申请时冻结，链上广播成功后正式扣减
资金费的特殊性

资金费是用户之间的零和转移，平台只是执行者。 这意味着它天然满足「总额守恒」—— 如果对账发现资金费环节出现总额变化， 一定是记账逻辑写错了（比如手续费被重复扣除， 或者某一方被扣了但对手方没有收到）。

04.7对账：让差异无处藏身

对账是资金系统最后也最重要的一道防线。它的目的不是「证明系统没问题」， 而是在问题扩大之前发现它。有效的对账必须覆盖三个层面。

图 04-D 三道防线。第一道防逻辑错误，第二道防累积偏差，第三道防外部风险（链上资产被盗、被冻结、被重组）。三道的检查频率与目的完全不同，缺一不可。

差异出现时怎么办

对账的目的是发现差异，而差异一旦出现，处理流程必须预先定义好， 否则现场会陷入混乱。推荐的处置顺序：

  1. 立即冻结风险敞口暂停该币种的提现。这是第一动作 —— 阻止损失扩大比查清原因更紧急。注意：暂停提现会影响所有用户，所以只冻结受影响的币种，不要全站暂停。
  2. 定位第一条不平的记录利用 balance_after 做二分查找，快速找到差异开始的序列号，而不是重算全部流水。
  3. 判断方向与规模是平台多给了用户（平台损失），还是少给了（用户损失）？涉及多少用户、多少钱？这决定了处置的紧急程度与沟通策略。
  4. 保留现场不要急着「修复数据」。先把相关流水、日志、事件快照完整导出并归档 —— 如果是安全事件，这些是取证材料，改了就无法追溯。
  5. 补偿而非修改确认原因后，通过追加冲正条目修正余额，而不是 UPDATE 历史记录。修改历史会让审计链断裂。
  6. 补上检测能力复盘时必须回答：为什么这道防线没能在更早的时候发现？如果现有的检查没能覆盖这个场景，就要把它加进对账规则。
第 04 章 · 检查清单

① 余额拆成可用/冻结/锁定三个分量，恒等式 Total = 三者之和成立；
② 冻结是状态转移而非扣款，撤单是反向搬运，幂等可重试；
③ 所有资金变动都产生复式账本条目，按币种借贷平衡；
④ 账本表禁止 UPDATE/DELETE，通过数据库权限强制；
⑤ 释放冻结额按累计成交量计算，保证终态精确归零；
⑥ 逐笔计算资金、批量提交事务，绝不做批量算账；
⑦ 「可提」是派生值而非存储字段；
⑧ 对账三道防线全部上线，差异处置流程预先定义。
