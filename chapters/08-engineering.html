技术栈与工程实践：把性能压到极限

选型决定了性能的天花板，工程实践决定了能否触及这个天花板。 这一章讲语言与存储的分工逻辑、撮合内核的性能工程、 可观测性三件套，以及一套能测出系统真实上限的压测方法。

选型矩阵 · 性能优化清单 · 压测方案

08.1语言选型：按职责分工，而不是全栈统一

「整个系统用一种语言」是管理上的偷懒，不是工程上的最优。 交易系统的不同部分对语言的要求差异极大， 按职责分工才能各取所长。

模块核心要求常见选择为什么
撮合内核 极致延迟、无 GC 停顿、确定性 C++ / Rust 可精确控制内存布局与分配；无运行时；能绑定 CPU 核心；延迟可预测
业务服务 开发效率、生态、并发处理 Go / Java Go 的 goroutine 适合 IO 密集；Java 生态成熟、JVM 调优手段丰富
风控与规则引擎 快速迭代、热更新 Java / Python（规则部分） 规则变化频繁，需要能快速上线而不重启核心服务
数据分析 批处理、统计、生态 Python / SQL 生态最丰富，开发效率最高，对延迟不敏感
前端 实时渲染、交互响应 TypeScript + React 类型安全；生态成熟；WebSocket 与高频渲染有成熟方案
多语言的代价必须正视

多语言不是免费的。它带来构建复杂度、调试难度、 跨语言序列化成本、以及团队技能分散。 因此引入第二种语言的判据应当很明确： 这门语言能否带来数量级的性能或安全提升？ 如果只是「20% 的性能提升」，用 Go 写完全够，不值得引入 C++。 撮合内核之所以值得用 C++，是因为它带来的是数量级的差异。

08.2存储选型：四类数据，四种库

试图用一种数据库装下所有数据，必然有一类数据很难受。 按访问模式分类是更实际的做法。

STORE 01

关系库 · MySQL / PostgreSQL

订单、账本、用户、提现。要求 ACID 事务与唯一约束。账本表单独部署，只追加不修改。

关键：分库分表按用户 ID，避免热点

STORE 02

内存库 · Redis

盘口缓存、会话、限流计数、幂等去重、排行榜。亚毫秒读写，可容忍故障时重建。

关键：明确哪些数据可以丢

STORE 03

消息队列 · Kafka / Pulsar

事件流、跨服务通知、异步任务。要求分区内有序、至少一次投递、可回溯重放。

关键：分区键的选择决定有序性范围

STORE 04

列式库 · ClickHouse

成交历史、K 线、风控日志、审计流水。高压缩比、聚合查询快、写多读少。

关键：不承担事务，只做分析

账本存储的特殊要求

账本是所有数据里最特殊的一类。它的要求可以总结为三条， 这三条决定了它不能和其他业务数据放在一起：

  • 隔离独立部署。账本表的写入量可能占全库的 60% 以上，与订单、用户表混在一起会互相影响。独立实例 + 独立磁盘是标准做法。
  • 只追加权限上禁止 UPDATE/DELETE。应用账号只有 INSERT 与 SELECT，这是靠数据库权限强制执行的，不靠代码自觉。
  • 可校验支持区间校验。能高效地回答「第 N 到第 M 条之间借贷是否平衡」，这要求 entry_no 上有索引且连续。

08.3事件流：系统的主干神经

在事件驱动的架构里，消息队列不是「解耦工具」， 而是系统的真相来源。所有状态都是从事件流推导出来的， 这意味着它的可靠性要求高于任何单个服务。

分区键决定有序性的边界

Kafka 只保证分区内有序。因此分区键的选择直接决定了 「什么范围内的事件是有序的」。

按交易对分区
  • 同一交易对的事件严格有序 —— 满足撮合要求
  • 不同交易对并行处理，吞吐量高
  • 单交易对的处理能力受单分区限制
  • 适用于撮合、行情类事件
按用户 ID 分区
  • 同一用户的事件严格有序 —— 满足资金操作要求
  • 用户之间互不影响，天然隔离
  • 热点用户（做市商）可能造成分区倾斜
  • 适用于账户、提现类事件
分区键选错的后果

如果撮合事件用「随机分区」，同一交易对的订单会落到不同分区， 下游消费者并行处理时无法保证顺序 —— 撮合结果将不可复现，前面所有关于确定性的设计全部失效。 分区键必须与「需要保序的业务边界」严格对应，这是设计事件流时的第一决策。

08.4撮合性能工程：把单线程压到极致

第 03 章讲了「为什么必须单线程」。这一节讲「单线程怎么做到每秒几十万笔」。 核心思路只有一条：消除一切非必要的 CPU 开销。

图 08-A 撮合内核的六项优化。它们的共同点是「把工作挪出去」而不是「把工作做得更快」 —— 这是低延迟系统优化的核心思路。把日志、持久化、校验全部移出热路径，比优化热路径本身的收益大得多。

延迟的真正构成

很多人以为「撮合慢是因为算法不够快」。实际上算法只占一小部分， 大部分延迟来自内存访问与同步原语：

操作典型耗时相对倍数
L1 缓存访问约 1 ns1×
L2 缓存访问约 4 ns4×
L3 缓存访问约 15 ns15×
主内存访问约 80 ns80×
一次互斥锁竞争约 20 ~ 100 ns20~100×
一次系统调用约 500 ns ~ 2 μs500~2000×
一次网络往返（同机房）约 100 μs100000×
读这张表得出的结论

一次网络往返 = 十万次缓存访问。 所以撮合内核里任何形式的远程调用都是不可接受的。 同样，一次系统调用的代价相当于 500 次内存访问 —— 这就是为什么「不写日志」不是洁癖，而是必要的性能纪律。 优化优先级应该是：先消除远程调用 → 再消除系统调用与锁 → 最后才优化算法。

08.5可观测性：让系统自己说出问题在哪

一个没有可观测性的分布式系统，在出故障时就是一堆黑盒。 可观测性由三个支柱构成，它们解决的是不同的问题。

支柱解决什么问题关键设计
指标 Metrics 「系统整体健康吗？趋势如何？」 用直方图而非平均值记录延迟 —— 平均值会掩盖长尾。P99 才是用户实际感受
日志 Logs 「这一笔具体发生了什么？」 结构化 JSON；必带 trace_id 与业务 ID；资金日志单独隔离并长期留存
追踪 Traces 「慢在哪一跳？谁调用了谁？」 全链路采样；撮合内核需要特殊的轻量埋点，不能引入可观测性开销

必须监控的核心指标

  • 延迟P50 / P90 / P99 / P99.9，按接口与交易对分别统计。只看平均值等于什么都没看。
  • 吞吐每秒订单数、成交数、事件数。要能按交易对下钻，快速定位是全局问题还是单交易对问题。
  • 队列定序器积压、消息队列 lag、线程池队列深度。积压是雪崩的前兆，比延迟更早发出预警。
  • 资金各币种余额总量、对账差异、冻结总额。这类指标应当作为业务指标监控，异常即 P0。
  • 错误按错误码分类统计，而不是笼统的「错误率」。余额不足导致的拒绝是正常业务，不该触发告警。
告警设计的一条原则

告警必须可行动。如果一个告警响了之后， 值班人员不知道该做什么，那这个告警就是噪音， 最终会导致所有人忽略告警（告警疲劳）。 每条告警都应该附上：可能的原因、排查步骤、止损动作。

08.6压测：测出系统的真实上限

压测最常见的错误是「测了一个假的场景」。 用固定请求、固定参数、固定节奏去压测，得到的是一个乐观的数字， 而真实流量有热点、有长尾、有突发。

有效压测的四个要求

  1. 流量模型要真实按真实业务比例构造流量：查询 : 下单 : 撤单 : 提现 ≈ 100 : 10 : 8 : 0.1。只压下单接口得到的数字没有意义，因为真实系统里查询占绝大多数。
  2. 数据分布要真实用户不是均匀的。少数活跃用户贡献大部分请求，部分交易对占据大部分流量。压测数据必须复现这种不均衡，否则测不出热点问题。
  3. 包含慢依赖数据库、缓存、消息队列都必须是真实的，且数据量要达到生产规模。用一个空数据库压测，索引还没建立起来，测出来的数字会严重偏高。
  4. 测到「拐点」而不是「峰值」逐步加压，观察延迟曲线。找到延迟开始非线性上升的那个点 —— 那才是系统的真实容量。峰值数字往往已经是在崩溃边缘。

图 08-B 压测要找的是拐点。拐点之前的容量是「安全的」，之后是「随时崩溃的」。实际容量规划应当取拐点的 60%~70%，为突发流量留出余量。

08.7调优案例：从 5 万到 50 万 TPS

下面是一个典型撮合内核的优化过程。注意每一步的收益量级 —— 它验证了前面那条结论：消除开销比优化算法有效得多。

步骤做了什么TPS提升
起点Java 实现，订单对象每笔新建，同步写日志，用 HashMap 维护价位50,000—
①对象池复用，消除 GC 压力90,0001.8×
②日志改为异步批量写入，移出热路径150,0001.7×
③价位结构改为有序数组 + 二分查找，替代 HashMap 遍历230,0001.5×
④改用 C++ 重写内核，精确控制内存布局400,0001.7×
⑤CPU 亲和绑定 + 关闭超线程 + 大页内存520,0001.3×
从案例中提炼的三条规律

① 前两步（消除 GC 与 IO）贡献了 3 倍提升， 而这两步都没有改变算法 —— 只是把开销挪走了。

② 换语言带来 1.7 倍，是在前面积累的基础上。 如果一上来就用 C++ 但保留原来的设计（每笔 new、同步写日志）， 性能不会比优化后的 Java 好多少。

③ 每一步之后都要重新压测定位新的瓶颈。 优化 A 之后瓶颈会转移到 B，凭直觉猜下一个瓶颈几乎总是猜错。

一个容易被忽略的瓶颈

当单交易对 TPS 达到几十万后，新的瓶颈往往不在撮合本身， 而在行情分发的带宽与下游消费者的处理能力。 此时继续优化撮合已经没有意义 —— 系统整体的上限由最慢的一环决定，而不是最快的一环。 这也是为什么容量规划必须做全链路压测，而不能只压单点。

第 08 章 · 检查清单

① 语言按职责分工，引入新语言的判据是数量级提升；
② 四类数据分四种存储，账本独立部署且只追加；
③ 消息队列分区键与业务保序边界严格对应；
④ 撮合内核零分配、零拷贝、零系统调用，CPU 亲和绑定；
⑤ 优化顺序：先消除远程调用与 IO，再优化算法；
⑥ 延迟用直方图统计，关注 P99 而非平均值；
⑦ 压测流量模型与数据分布贴近真实，测拐点而非峰值；
⑧ 容量规划取拐点的 60%~70%，全链路压测。
